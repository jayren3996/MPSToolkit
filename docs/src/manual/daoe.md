# DAOE

*Diagonal projector MPOs that damp operator components by operator size to preserve hydrodynamic transport while suppressing entanglement growth.*

`MPSToolkit.jl` provides two such projectors:

- `pauli_daoe_projector` for the original DAOE construction, where operator size is the Pauli weight (the number of non-identity factors in a Pauli string);
- `fdaoe_projector` for the fermionic generalization (FDAOE), where size is a Jordan–Wigner-aware fermionic weight.

Both act in the Pauli operator space described on the [Operator Space](operator-space.md) page, on site indices built by `pauli_siteinds` in the default local ordering ``(I, X, Y, Z)``. Read that page first if the vectorized Pauli-basis picture is unfamiliar.

## Background

In the Heisenberg picture an initially local operator ``O(0)`` evolves as ``O(t) = e^{iHt}\, O(0)\, e^{-iHt}``. Even when ``O(0)`` is supported on a single site, the commutators generated by ``H`` dress it with ever longer and more numerous Pauli strings: the operator *spreads*. In a generic (chaotic, non-integrable) chain the support grows ballistically — a light cone of width ``\sim v_B t`` set by the butterfly velocity — and, more damagingly for tensor networks, the operator's internal structure becomes increasingly random. Expanding ``O(t)`` in the local Pauli basis,

```math
O(t) = \sum_{\boldsymbol{\mu}} c_{\boldsymbol{\mu}}(t)\, \sigma^{\mu_1} \otimes \cdots \otimes \sigma^{\mu_N},
\qquad \mu_j \in \{I, X, Y, Z\},
```

the weight ``|c_{\boldsymbol{\mu}}(t)|^2`` flows from short, low-weight strings into an exponentially growing cloud of long, high-weight ones. When ``O(t)`` is represented as a matrix product operator (equivalently, as a matrix product *state* in the doubled Pauli space), this proliferation shows up as **operator-space entanglement** that grows roughly linearly in time, forcing the bond dimension to grow exponentially. Exact MPO evolution therefore stalls after a short time, just as it does for entanglement growth after a quench.

The key physical observation behind DAOE is that this expensive high-weight cloud is largely **irrelevant to transport**. Hydrodynamic quantities — diffusion constants, conductivities, the long-time tails of autocorrelators — are governed by the slow, conserved, *low-weight* part of the operator. The fast operator-spreading front carries most of the entanglement but contributes a vanishing fraction of the slowly relaxing signal: under chaotic dynamics, weight that has scrambled into very long strings behaves like a structureless bath and, on average, no longer feeds back coherently into the few-body observables one measures.

DAOE exploits this by adding an **artificial dissipation that targets operator size directly** rather than bond dimension. Define the size (Pauli weight) of a basis string as the number of non-identity factors,

```math
\ell(\boldsymbol{\mu}) = \#\{\, j : \mu_j \neq I \,\}.
```

DAOE leaves short strings untouched and exponentially damps the amplitude of long ones beyond a cutoff size ``\ell^\ast``,

```math
c_{\boldsymbol{\mu}} \;\longmapsto\; D(\boldsymbol{\mu})\, c_{\boldsymbol{\mu}},
\qquad
D(\boldsymbol{\mu}) =
\begin{cases}
1, & \ell(\boldsymbol{\mu}) \le \ell^\ast,\\[2pt]
e^{-\gamma\,(\ell(\boldsymbol{\mu}) - \ell^\ast)}, & \ell(\boldsymbol{\mu}) > \ell^\ast.
\end{cases}
```

Here the cutoff is the keyword `lstar` (``\ell^\ast``) and the per-unit damping strength is `gamma` (``\gamma``). The damping is multiplicative and diagonal in the Pauli basis, so the operator that implements it is a **diagonal MPO** — exactly what `pauli_daoe_projector` returns. Interleaving it with ordinary Heisenberg time steps does two things at once:

- it caps operator-space entanglement, because strings longer than ``\ell^\ast`` are continuously suppressed and never accumulate enough weight to inflate the bond dimension; and
- it preserves the slow hydrodynamic modes, because every string with ``\ell \le \ell^\ast`` — in particular the conserved densities and their short dressings — passes through untouched (``D = 1``).

The cutoff ``\ell^\ast`` is the central convergence knob. Larger ``\ell^\ast`` keeps more of the operator exactly (more accurate, more expensive); ``\gamma`` controls how hard the tail beyond the cutoff is cut. Genuine hydrodynamic results are obtained by checking that transport observables are insensitive to ``\ell^\ast`` and ``\gamma`` over a window, i.e. that one is dissipating only the scrambled front and not the physics. Because the damping is artificial, it is a controlled approximation, not an exact unitary step; the projectors are deliberately exposed as plain MPOs so you compose them into your own operator-space pipeline rather than hiding the approximation inside a black box.

## DAOE vs FDAOE

DAOE and FDAOE differ only in *which* notion of operator size is damped.

**DAOE — Pauli weight.** `pauli_daoe_projector` counts non-identity Pauli factors, ``\ell(\boldsymbol{\mu})`` above. This is the natural size measure for spin chains written in a local Pauli basis, where operator complexity is faithfully tracked by how many sites carry a non-trivial ``X``, ``Y``, or ``Z``.

**FDAOE — fermionic weight.** In fermionic problems the relevant operators are products of Majorana/fermion operators, and the Jordan–Wigner transformation maps a single fermion bilinear onto a Pauli string decorated with a long ``Z`` *string* running back to the boundary. A physically short fermionic operator can therefore have a large Pauli weight purely because of its Jordan–Wigner tail, so plain Pauli-weight damping would penalize it for free and distort the operator hierarchy that actually matters for fermionic transport. FDAOE fixes this by measuring size with a Jordan–Wigner-aware fermionic (Majorana) weight: the projector tracks the fermion parity carried through each bond and assigns weight to a local symbol according to whether it lies on or off a Jordan–Wigner string, so that a Jordan–Wigner ``Z`` tail costs nothing while genuine fermionic content is counted. `fdaoe_projector` uses the cutoff `wstar` (``w^\ast``) on this fermionic weight, with the same exponential damping law beyond the cutoff.

Practical rule of thumb (keep this guidance):

- use `pauli_daoe_projector` for spin models and Pauli-basis transport calculations;
- use `fdaoe_projector` when fermionic structure matters and Pauli-weight damping would distort the relevant operator hierarchy.

In both cases the result is a diagonal MPO over the same ``(I, X, Y, Z)`` Pauli-basis sites, and the two share an identical interface apart from the cutoff keyword (`lstar` vs `wstar`).

## Examples

The damping factor for a Pauli string under `pauli_daoe_projector` is ``e^{-\gamma(\ell-\ell^\ast)}`` for weight ``\ell > \ell^\ast`` and ``1`` otherwise. The snippet below builds the projector and inspects this on two representative strings via the Hilbert–Schmidt overlap ``\langle O, P\,O\rangle`` (with `inner` and `apply`):

```julia
using MPSToolkit
using ITensors
using ITensorMPS

sites = pauli_siteinds(8)

# Preserve Pauli weight up to lstar; damp each extra non-identity factor by exp(-gamma).
projector = pauli_daoe_projector(sites; lstar=3, gamma=0.15)

# A weight-1 string (X on site 1) is below the cutoff and is preserved exactly.
light = pauli_basis_state(sites, ["X", "I", "I", "I", "I", "I", "I", "I"])

# A weight-5 string sits two units above lstar = 3, so it is damped by exp(-2*gamma).
heavy = pauli_basis_state(sites, ["X", "Y", "Z", "X", "Y", "I", "I", "I"])

light_overlap = inner(light, apply(projector, light; maxdim=64, cutoff=0.0))
heavy_overlap = inner(heavy, apply(projector, heavy; maxdim=64, cutoff=0.0))
```

Here `light_overlap` is ``1`` (the weight-1 string is untouched) while `heavy_overlap` is ``e^{-2\gamma}`` for `gamma = 0.15`, since the weight-5 string is two units beyond `lstar = 3`. The keywords are exactly:

- `lstar`: the preserved Pauli-weight cutoff. Strings with weight ``\le`` `lstar` are kept exactly; heavier strings are damped. It must be nonnegative; the projector's bond dimension is `lstar + 1`.
- `gamma`: the damping strength per unit of weight above the cutoff. Larger `gamma` cuts the high-weight tail harder; `gamma = 0` recovers the identity.

`fdaoe_projector` has the same shape, with `wstar` (the fermionic Majorana-weight cutoff) in place of `lstar`:

```julia
using MPSToolkit
using ITensors
using ITensorMPS

sites = pauli_siteinds(8)

# Damp fermionic (Jordan-Wigner) weight beyond wstar by exp(-gamma) per unit.
projector = fdaoe_projector(sites; wstar=3, gamma=0.15)

state = pauli_basis_state(sites, ["X", "Z", "Z", "X", "I", "I", "I", "I"])
overlap = inner(state, apply(projector, state; maxdim=64, cutoff=0.0))
```

The `fdaoe_projector` keywords are:

- `wstar`: the fermionic Majorana-weight cutoff. Operator strings whose fermionic weight exceeds `wstar` are exponentially damped, while the Jordan–Wigner ``Z`` strings needed to write a short fermionic operator are not penalized. It must be nonnegative; the bond dimension is `wstar + 2`.
- `gamma`: the damping strength per unit of fermionic weight above `wstar`, identical in role to the DAOE case.

For both projectors, `maxdim` and `cutoff` are the standard `apply` options controlling the compression of the resulting MPO/MPS: `maxdim` bounds bond growth and `cutoff` discards singular values below the threshold. Constructing the projector itself is cheap — its bond dimension is fixed by the cutoff (`lstar + 1` or `wstar + 2`), independent of how scrambled the operator becomes.

## Using the projectors

`pauli_daoe_projector` and `fdaoe_projector` return ordinary diagonal `MPO`s, so they slot into any operator-space pipeline rather than dictating one. The intended pattern is to alternate ordinary Heisenberg (operator-space) time evolution with periodic applications of the projector:

```julia
using MPSToolkit
using ITensors
using ITensorMPS

nsites = 8
sites = pauli_siteinds(nsites)

# An operator-space state: e.g. a local Z probing spin transport.
state = pauli_basis_state(sites, ["Z", "I", "I", "I", "I", "I", "I", "I"])

# Operator-space (Heisenberg) TEBD evolution over a short window.
evolution = tebd_strang_evolution(
  nsites,
  0.05;
  local_hamiltonian=(bond, weight) -> weight * spinhalf_tfim_bond_hamiltonian(nsites, bond; J=1.0, g=0.8),
  map_hamiltonian=pauli_gate_from_hamiltonian,
  maxdim=64,
  cutoff=1e-12,
)

projector = pauli_daoe_projector(sites; lstar=3, gamma=0.15)

# Repeatedly evolve, then damp the scrambled high-weight tail.
for _ in 1:10
  evolve!(state, evolution)
  state = apply(projector, state; maxdim=64, cutoff=1e-12)
end
```

A few points on composing them well:

- **Cadence and strength trade off.** Applying a strong projector every step versus a weaker one less often both control entanglement; what matters physically is the *rate* of artificial dissipation. Treat `lstar`/`wstar`, `gamma`, and the application cadence together as the convergence knobs, and confirm transport observables are stable across a window of these choices.
- **Pick the size measure that matches the model.** Use `pauli_daoe_projector` for spin/Pauli-basis transport and `fdaoe_projector` for fermionic problems, per the rule of thumb above.
- **DAOE is complementary to DMT.** DAOE damps by operator *size*; the [DMT](dmt.md) backend (`DMTGateEvolution`, `dmt_evolve!`) instead changes the local truncation rule to protect the identity/low-weight component at every bond. Both target hydrodynamic transport while taming entanglement, and can be used in the same operator-space stack. For general operator-space TEBD without a transport bias, evolve with `LocalGateEvolution` and the Pauli-basis helpers from the [Operator Space](operator-space.md) page.
- **These projectors are one-sided and change the trace.** A DAOE/FDAOE projector is a *diagonal damping* MPO applied once (`apply(projector, state)`), not a Hermitian ``P\rho P`` sandwich like the PXP constraint projector ``P_G``. Damping high-weight strings rescales operator content, so the projector is not trace-preserving and is **not** a drop-in replacement for a constraint projector inside `constrained_dmt_evolve!` (which is built around a trace-preserving ``P_G``). Use DAOE/FDAOE with the plain `evolve!` / `apply` cadence shown above; reach for `constrained_dmt_evolve!` only with an actual constraint projector such as `pauli_pxp_constraint_projector`.
